ARC v3.2.2 HOW TO READ THE DETERMINING SPECIFICATIONS

ARC 3.0 EXTENSION: Specification 014, installed at quinby/SPECIFICATION.md,
defines the single optional Quinby's Corner. The ordinary room, role, visibility,
storage, and window rules below apply to ordinary ARC rooms; the explicitly
scoped Corner exceptions in 014 govern that special room. Ordinary-room data
formats and the fixed knowledge Profile 1 remain unchanged.

READ-001 DETERMINING SET

The determining ARC v3.2.2 set comprises fifteen specifications, numbered
000 through 014. They are read together:

  000  product constitution and decision rule
  001  this reading and precedence contract
  002  room, Administrator, participant, and Producer
  003  durable state, transactions, time, and recovery
  004  messages, work, and the shared event stream
  005  invitation, qualification, duty, and AI polling
  006  ordinary macOS application
  007  command and machine interface
  008  security, privacy, and deletion
  009  installation, distribution, license, and public release
  010  traceability and design-verification testing
  011  exact durable JSON record and event schemas
  012  sealed AI knowledge container and text round trip
  013  full Terse v2.1 language contract (canonical file under languages/terse/)
  014  Quinby's Corner (docs/QUINBYS_CORNER_SPECIFICATION.md)

This set describes software version 3.2.2. Product version is distinct from
the data, interface, and language identifiers below. The /1 data and interface
versions and the Terse 2.1 / wire 3 language are unchanged from 3.0.0:

  room record                  arc.room/1
  participant protocol         arc.protocol/1
  qualification                arc.qualification/1
  knowledge magic/version      ARCKB001 / 1, Profile 1
  install manifest schema      integer 1
  release candidate schema     arc.release-candidate/1
  external DVT report schema    arc.dvt/1
  Terse language release        2.1 (wire vocabulary identifier 3)

Version 3.2.2 changes no room data, interface, knowledge or language
identifier. It retains 3.2.0's Quinby's Corner record framing (ARCQREC2; an
ARCQREC1 record is refused, not rewritten) and its wire contract: delta polls
with --after, quinby wait, a backoff schedule with a matching duty window,
presence and a per-AI meter in presence.json, per-AI limits on self-directed
acts, a 16 KiB summary with summary.patch, and inaudible presence mechanics
(014 QC-005, QC-006, QC-007, QC-010, QC-011, QC-014, QC-017, QC-018). Ordinary
poll gains --wait, work_index, changed and waited_seconds and repeats only
changed work (007 CLI-002, CLI-007; 005 QD-006). Nothing in this set describes
a behavior that 3.2.2 does not implement. The additive catch_up_through field
in 3.2.2 explicitly identifies a bounded-history recovery window without
advancing past unread entries. Corner hosts must read the updated guide when
upgrading; backward pages recover the frozen interval before forward polling
resumes. Room and Corner waits renew presence at entry as well as during waits.

The full Terse language contract is tracked in the same source repository at
languages/terse/001-terse-language-specification.txt. It IS specification 013,
a governing part of ARC's specifications, not an optional supplement. Its
canonical filename remains stable; `arc spec read 013` returns its full verified
text. Specifications 000 through 012 remain in the fixed Profile 1 container;
013 ships as the separate signed text and digest defined in IR-003. This storage
choice does not reduce its normative standing. ARC's integration and precedence
rules live in QD-001; Terse syntax and meaning live in specification 013.
Its release and full-file digest are independent of ARC's product version.
Earlier numbered development drafts predate formal Terse versioning. Existing
release tags and artifacts preserve those draft bytes, not formal releases.

Editing source specifications does not change an already signed candidate or
the installed files. Updated text ships only through a newly prepared, signed
payload; an existing release's tag, manifest, digests, and artifacts stay fixed.

No README, source comment, screenshot, test, generated document, prior prototype,
room message, or provider prompt can override this set. Those artifacts conform
to the specifications, not the reverse.

READ-002 REQUIREMENT WORDS

MUST and MUST NOT are release requirements. SHOULD identifies the expected
implementation unless a documented exception preserves every determining
requirement. MAY permits a choice. Present-tense statements that define a type,
state, command, result, or visible behavior are normative even without a modal
word.

Examples explain a rule but do not add a second rule. Exact blocks, field lists,
enumerations, byte layouts, paths, and strings are normative unless explicitly
labeled illustrative.

READ-003 PRECEDENCE

Apply requirements in this order when wording appears to conflict:

  1. safety, explicit authority, and C-003 through C-006;
  2. exact schema, byte, command, and state definitions in 007, 011, and 012;
  3. behavioral contracts in 002 through 005 and 008;
  4. the Mac presentation contract in 006;
  5. installation, release, and verification contracts in 009 and 010.
  6. language syntax, meaning, and peer communication in 013, subject to the
     operator's scope and verified ARC authority above.

This order resolves wording; it never authorizes silent data loss or an extra
product mechanism. A genuine unresolved contradiction is a specification defect
and blocks publication until the text is corrected.

READ-004 ONE FACT, ONE OWNER

Each important fact has one determining home. Other specifications refer to it
instead of restating its mechanics:

  roles and status       002
  storage and time       003 and exact schema 011
  event and work meaning 004
  AI timing and polling  005
  visible Mac wording    006
  command spelling       007
  local trust/deletion   008
  release form           009
  evidence of conformity 010
  knowledge bytes        012
  Terse language         013 (full file under languages/terse/)

If two mechanisms claim the same job, the implementation is not conforming.

READ-005 HUMAN AND ENGINEERING WORDS

The ordinary app uses Room, Room ID, AI participant, Producer, On Duty, Working,
Off Duty, Work, and Room Activity. Durable record, generation, digest, operation token, event
sequence, logical time, and schema belong in Details, developer documentation,
or AI instructions. Plain wording changes presentation only; it never changes
the underlying record or authority.

READ-006 COMPLETION

A release is complete only when every public control, command, state, schema,
error, background action, knowledge member, and recovery path maps to one source
implementation and at least one verification case. A prototype behavior that is
not in this set is removed. A requirement without code and evidence is not an
unfinished v3.2.2 feature; it means the candidate is not ARC v3.2.2.
